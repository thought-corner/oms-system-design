# PRD — 커머스 주문 서비스 (monolithic → MSA)

> 문서 번호 0001 · 2026-09-21 · 용어는 §2 을 따른다.

## 1. 배경 · 목적

- **구성**: Kotlin 2.3.21 · Spring Boot 4.1.1 · Gradle 9.7.1 단일 모듈 모놀리스, 패키지 `com.project.msa`.
- **문제**: 주문 결제는 "재고 차감 + 포인트 사용 + 주문 완료" 세 문맥의 상태를 한꺼번에 바꾼다. 한 DB·한 트랜잭션이면 쉽지만, 문맥을 서비스로 쪼개면 그 보장이 사라진다.
- **목적**: 먼저 **모놀리스에서 원자성·멱등성·동시성 요구사항 (§4)을 만족하는 기준선**(Phase 1)을 갖추고, **문맥을 분리했을 때 같은 요구사항을 어떻게 지키는지**(분산 트랜잭션) 검증한다.
  분리 이후에도 **Phase 1 테스트 스위트가 그대로 통과**하는 것이 완료 기준이다. 분리 방식 (Saga·Outbox 등)은 착수 시 `decisions.md` 에서 정하고, 요구사항이 바뀌면 이 문서를 개정하지 말고
  `docs/0002_*.md` 를 새로 쓴다.
- **대상**: 이 레포를 만드는 사람 본인. 외부 소비자·프런트 없음.

## 2. 용어

이 문서에서 특히 구분하는 말:
**주문 생성**(저장만) vs **주문 결제**(차감·완료) · **재고**(`Product.quantity`) vs **주문 수량**(`OrderItem.quantity`) · **잔액** vs **사용 금액**
vs **총액**.

## 3. 기능 요구사항

### FR-1 주문 생성 — `POST /order`

- 입력: `{ userId, orderItems: [{ productId, quantity }] }` (quantity = 주문 수량). `userId` 는 클라이언트가 주는 값을 그대로 믿는다.
- 검증: 항목이 1개 이상, 각 주문 수량은 1 이상. 아니면 `400 INVALID_ORDER` — 결제 시 재고·잔액이 **늘어나는** 경로를 입구에서 막는다.
- 처리: `orders` 에 주문 1건 (주인 `userId`, 상태 `CREATED`), `order_items` 에 항목 N건 저장.
- 출력: `{ orderId }`.
- **재고·포인트를 건드리지 않는다.** 이 시점엔 재고 부족·잔액 부족·`userId` 의 포인트 존재 여부를 검사하지 않는다 (결제 시 검사).

### FR-2 주문 결제 — `POST /order/place`

- 입력: `{ orderId }`. 사용자는 요청에 없다 — **주문이 주인 (`userId`)을 알고 있으므로** 그 사용자의 포인트에서 차감한다. 다른 사용자가 남의 주문을 결제하는 경로는 없다.
- 처리 순서 (단일 트랜잭션):
    1. 주문 조회. 없으면 실패.
    2. 이미 `COMPLETED` 면 **아무것도 하지 않고 성공 응답**(FR-2 의 멱등 경로, NFR-2). 그 밖의 상태에서 결제 이벤트가 허용되는지는 상태 기계가 판정한다 — 허용되지 않으면
       `409 INVALID_ORDER_STATE_TRANSITION`.
    3. 주문 항목마다 재고 차감 (`ProductService.buy`) 하고 항목 총액 (`price × 주문 수량`)을 합산해 총액을 만든다.
    4. 결제 (`PaymentService.pay`): 주문의 `userId` 포인트에서 총액만큼 사용 (`PointService.use`) 하고, 외부 결제 승인 (실제 PG 없음 — 3초 지연으로 대신) 을
       거쳐 `payments` 에 결제 1건 (`PAID`, `paidAt`) 을 기록한다. 그 사용자의 포인트가 없으면 실패. 주문당 결제는 1건 (`orderId` unique).
    5. 주문 상태 `CREATED → COMPLETED`.
- 출력: 본문 없음 (HTTP 200).
- 총액은 저장하지 않고 매번 계산한다. 값을 지어내지 않는다.

### FR-3 초기 데이터 시드

- 기동 시 포인트 사용자 3명 (userId 1·2·3, 잔액 각 10000) · 상품 2개 (재고 100 / 단가 100, 재고 100 / 단가 200).
- `ddl-auto: create` 라 **기동마다 스키마와 데이터가 초기화**된다.

## 4. 비기능 요구사항

> 이 절의 "현재 수단"과 NFR-4 표는 모놀리스 기준선(Phase 1) 시점의 것이다. 분리 이후의 현재 수단과 실패 코드는 `docs/0002`·`docs/0003`(§3 서비스 간 계약)이 정본이다(§1).

### NFR-1 원자성

결제 중 **어느 한 단계라도 실패하면 재고·포인트·주문 상태 모두 결제 전으로 되돌린다.**
부분 차감 (재고는 빠졌는데 포인트는 안 빠짐, 또는 그 반대)은 어떤 경우에도 남지 않는다.

- 현재 수단: 세 문맥이 한 DB · `OrderService.placeOrder` 의 한 `@Transactional`(`ProductService`·`PaymentService`(→ `PointService`) 의 `@Transactional` 이 참여). 예외 → 롤백.
  이 참여). 예외 → 롤백.
- MSA 분리 후: 이 수단이 사라진다 — 분리 단계의 핵심 과제 (§1).

### NFR-2 멱등성

같은 `orderId` 로 결제를 **몇 번 요청해도 재고·포인트는 정확히 한 번만 차감**된다.

- 현재 수단: `COMPLETED` 면 즉시 반환 (FR-2 2단계).

### NFR-3 동시성

같은 `orderId` 로 **동시에** 결제 요청이 와도 차감은 한 번만 일어난다. 나머지 요청은 실패하거나 (현재) 결제 완료 결과를 돌려준다.

- 현재 수단: **MySQL 행 락**. 주문은 `SELECT … FOR UPDATE NOWAIT` — 같은 주문의 두 번째 요청은 기다리지 않고 `409 ORDER_LOCKED`(잠시 뒤 재요청하면 NFR-2
  경로로 성공). 재고·포인트는 `FOR UPDATE`(대기형)로 읽어 **다른 주문이 같은 상품·사용자를 차감해도 직렬화**된다 (lost update 없음). 잠금 순서 orders → products
  (productId 오름차순) → points 로 데드락을 막는다.
- 알려진 한계: 행 락은 한 DB 안에서만 유효 — 문맥이 DB 를 나눠 갖는 순간 (분리 단계) 다른 수단이 필요하다 — 분리 단계에서 결정(§1). 락 대기 중엔 요청 스레드와 DB 커넥션이 묶인다.

### NFR-4 실패 응답

실패는 **HTTP 상태 + 본문 `{ code, message }`** 로 구분된다. 클라이언트는 `code` 로 분기하고 `message` 는 사람이 읽는다. 내부 오류 메시지는 응답에 싣지 않는다. 정본은
`exception/*ErrorCode` enum — 아래 표는 그 사본이다.

| 원인                                               | 상태                               | `code`                                                      |
|----------------------------------------------------|------------------------------------|-------------------------------------------------------------|
| 요청 본문을 읽을 수 없음(JSON 오류·필수 필드 누락) | 400                                | `MALFORMED_REQUEST`                                         |
| 빈 항목 · 주문 수량 0 이하                         | 400                                | `INVALID_ORDER`                                             |
| 주문 · 상품 · 사용자 포인트 없음                   | 404                                | `ORDER_NOT_FOUND` · `PRODUCT_NOT_FOUND` · `POINT_NOT_FOUND` |
| 재고 부족 · 잔액 부족                              | 409                                | `INSUFFICIENT_STOCK` · `INSUFFICIENT_POINT`                 |
| 같은 주문을 다른 요청이 결제 중                    | 409                                | `ORDER_LOCKED`                                              |
| 현재 주문 상태에서 허용되지 않는 전이              | 409                                | `INVALID_ORDER_STATE_TRANSITION`                            |
| 경로 없음 · 메서드 불허 등 HTTP 계층 오류          | Spring 이 정한 상태(404·405·415 …) | `HTTP_<상태>`                                               |
| 그 밖의 오류                                       | 500                                | `INTERNAL_ERROR`                                            |
