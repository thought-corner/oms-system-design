# 비동기 사가 오케스트레이션 KPI 리포트

- **측정일**: 2026-09-26
- **대상**: 주문 결제 (`POST /order/place`) — 재고 차감 → 포인트 사용 → 결제를 서비스 셋이 메시지로 이어서 처리한다 (Kafka 메시지 + Outbox)
- **질문**: 결제 도중 서버·DB·메시지 서버가 망가져도, 복구된 뒤 고객의 재고·포인트·결제가 정확히 맞는가

## 시나리오

### S0 장애가 없을 때

![S0 시퀀스. 202를 0.02초에 돌려주고 재고·포인트·결제 (외부 승인 3초)를 차례로 처리해 4.34초에 완료한다](scenario/비동기-S0-정상-결제.svg)

- **Given** 사용자 1이 상품1 2개와 상품2 1개 (400원)를 주문했다.
- **When** 주문을 결제하면
- **Then** 접수되고, 주문이 결제 완료 (`COMPLETED`)가 된다.
- **Then** 재고·포인트가 한 번 빠지고 결제가 1건 기록되며, 6초 안에 끝난다.

### S1 같은 주문에 결제 요청 5건이 동시에 올 때

![S1 시퀀스. 5건 중 1건만 접수되고 나머지 4건은 409 ORDER_LOCKED를 받는다](scenario/비동기-S1-결제-연타-중복-차단.svg)

- **Given** 결제 전 주문 하나가 있다.
- **When** 다섯 요청이 한꺼번에 결제를 시작하면
- **Then** 정확히 1건만 접수되고, 나머지는 "처리 중" 거절 (`409 ORDER_LOCKED`)을 받는다.
- **Then** 재고·포인트·결제가 한 번만 반영된다.

### S2 재고보다 많이 주문했을 때

![S2 시퀀스. 재고 부족 응답을 받으면 취소 요청 셋을 한꺼번에 보내고 0.85초에 실패로 확정한다](scenario/비동기-S2-재고-부족-취소.svg)

- **Given** 재고 100개인 상품1을 500개 주문했다.
- **When** 주문을 결제하면
- **Then** 주문이 결제 실패 (`FAILED`)로 확정되고, 조회하면 사유 "재고 부족" (`INSUFFICIENT_STOCK`)이 보인다.
- **Then** 재고·포인트는 그대로이고 결제 기록이 없으며, 2초 안에 끝난다.

### S3 잔액보다 비싼 주문일 때

![S3 시퀀스. 재고 60개 차감 뒤 포인트가 부족하면 취소 처리로 재고를 되돌리고 1.43초에 실패로 확정한다](scenario/비동기-S3-잔액-부족-취소.svg)

- **Given** 잔액 10,000원인 사용자 2가 상품2 60개 (12,000원)를 주문했다.
- **When** 주문을 결제하면
- **Then** 주문이 결제 실패로 확정되고, 사유 "잔액 부족" (`INSUFFICIENT_POINT`)이 보인다.
- **Then** 먼저 뺀 재고 60개가 되돌아와 최종 차감량이 0이고, 2초 안에 끝난다.

### S4 실패한 결제를 같은 키로 다시 요청할 때

![S4 시퀀스. 같은 요청 키의 재요청은 새 결제 없이 접수 응답만 받고, 조회는 처음 실패 결과를 보여 준다](scenario/비동기-S4-같은-요청-재전송.svg)

- **Given** S2에서 실패한 주문이 있다.
- **When** S2와 같은 요청 키 (`Idempotency-Key`)로 다시 결제하면
- **Then** 접수 응답은 오지만 새 결제가 시작되지 않는다.
- **Then** 조회하면 처음 실패 결과 ("재고 부족")가 그대로 보인다.

### S5 결제 서버가 죽어 있을 때

![S5 시퀀스. 결제 서버가 죽은 동안 결제 요청이 Kafka에 남고 66초에 감시 작업이 다시 보낸다. 94초에 재기동하자 결제 1건만 하고 100.8초에 완료한다](scenario/비동기-S5-결제-서버-장애-후-완료.svg)

- **Given** 결제 서버를 강제로 종료했다.
- **When** 주문을 결제하고 90초 뒤 결제 서버를 다시 띄우면
- **Then** 장애 중 조회는 "결제 처리 중"이고, 결제를 취소하지 않는다.
- **Then** 서버가 돌아오면 결제를 마저 완료하고, 결제는 1건이다.

### S6 결제 승인을 기다리는 중에 주문 서버가 죽을 때

![S6 시퀀스. 결제 대기 중 주문 서버가 죽고 5.3초에 재기동하지만 46.2초에야 결제 결과를 읽기 시작해 46.4초에 완료한다](scenario/비동기-S6-주문-서버-재시작-후-완료.svg)

- **Given** 결제 전 주문 하나가 있다.
- **When** 결제 승인을 기다리는 사이 주문 서버를 강제로 종료하고 곧바로 다시 띄우면
- **Then** 고객은 이미 접수 응답을 받은 뒤라 영향이 없고, 결제를 취소하지 않는다.
- **Then** 주문 서버가 남아 있던 결제 결과를 이어 받아 완료하고, 결제는 한 번이다.

### S7 포인트 DB에 2분 동안 접속할 수 없을 때

![S7 시퀀스. 포인트 서버가 DB 연결을 30초씩 기다리며 다시 시도하는 동안 감시 작업이 요청을 다시 보내고, 120초에 DB가 돌아오자 125.4초에 완료한다](scenario/비동기-S7-포인트-DB-장애-후-완료.svg)

- **Given** 포인트 서버가 DB에 접속하지 못하게 막았다.
- **When** 주문을 결제하고 120초 뒤 막은 것을 풀면
- **Then** 장애 중 조회는 "결제 처리 중"이고, 결제를 취소하지 않는다.
- **Then** 결제를 마저 완료하고 재고·포인트·결제가 한 번씩이며, 운영자 알림은 없다.

### S8 메시지 발송기가 죽어 있을 때

![S8 시퀀스. 메시지 발송기가 죽은 동안 재고 차감 요청이 DB에 남고 감시 작업은 다시 보내지 않고 기다린다. 92초에 재기동하자 96.6초에 완료한다](scenario/비동기-S8-메시지-발송기-장애-후-완료.svg)

- **Given** 메시지 발송기를 강제로 종료했다.
- **When** 주문을 결제하고 90초 뒤 다시 띄우면
- **Then** 장애 중 요청은 DB에 남아 있고, 감시 작업은 중복 요청을 보내지 않고 기다린다.
- **Then** 발송기가 돌아오면 결제를 마저 완료하고, 재고·포인트·결제가 한 번씩이다.

### S9 처리할 수 없는 잘못된 메시지가 들어올 때

![S9 시퀀스. 깨진 재고 차감 요청은 재시도 없이 별도 보관함으로 빠지고 운영자 알림이 나며, 같은 줄의 정상 주문은 4.52초에 완료한다](scenario/비동기-S9-깨진-메시지-격리.svg)

- **Given** 곧 결제할 주문과 같은 줄 (같은 파티션)에 깨진 메시지를 넣었다.
- **When** 그 주문을 결제하면
- **Then** 깨진 메시지는 다시 시도하지 않고 별도 보관함 (DLT)으로 빠지며, 운영자 알림이 1건 나간다.
- **Then** 정상 주문은 기다리지 않고 6초 안에 완료된다.

### S10 이미 처리한 메시지를 다시 받을 때

![S10 시퀀스. 네 서버를 죽이고 읽은 위치를 되돌려 재기동하면 이미 처리한 요청 8건과 결과 8건이 다시 오지만, 모두 차감 없이 처리되거나 무시되어 기록은 그대로다](scenario/비동기-S10-메시지-재수신.svg)

- **Given** 주문 A는 결제 완료, 주문 B는 잔액 부족으로 취소 처리까지 끝났다.
- **When** 네 서버를 강제로 종료하고, 두 주문 이전 위치부터 메시지를 다시 읽게 한 뒤 다시 띄우면
- **Then** 요청 8건과 결과 8건을 다시 받지만 재고·포인트·결제 기록이 전혀 바뀌지 않는다.
- **Then** 두 주문의 상태가 그대로이고, 운영자 알림이 없다.

### S11 결제가 들어오는 중에 메시지 서버 한 대가 죽을 때

![S11 시퀀스. 메시지 서버 한 대를 죽이자 메시지 발송기가 약 10초 멈추고, 풀린 뒤 결제 요청이 몰려 결제 서버에서 최대 16초 기다린다. 60건 모두 완료된다](scenario/비동기-S11-메시지-서버-장애.svg)

- **Given** 메시지 서버 3대가 일을 7개씩 나눠 맡고 있다.
- **When** 결제를 0.5초마다 60건 넣는 도중, 일을 가장 많이 맡은 서버를 강제로 종료하면
- **Then** 모든 결제 요청이 접수되고, 60건 모두 취소 없이 결제 완료된다.
- **Then** 운영자 알림과 발송 실패가 0건이다.

### S12 결제 승인을 기다리는 동안 취소가 먼저 끝날 때

![S12 시퀀스. 늦게 온 결제 요청이 3초를 기다리는 동안 주문 서버의 취소 요청이 먼저 처리되고, 대기를 마친 결제는 취소됨 표시를 보고 거부돼 결제 기록이 생기지 않는다](scenario/비동기-S12-승인-대기-중-취소.svg)

- **Given** 잔액 부족으로 취소될 주문에, 같은 주문의 늦은 결제 요청이 도착해 외부 승인 대기를 시작했다.
- **When** 대기 중에 주문 서버의 취소 요청이 먼저 처리되면
- **Then** 주문은 결제 실패로 확정되고, 대기를 마친 결제는 거부돼 결제 기록이 0건이다.

### 부하 측정 결제 요청이 초당 10건씩 몰릴 때

- **Given** 재고와 잔액을 넉넉히 채웠다.
- **When** 결제 요청을 초당 4건씩 30초, 이어서 초당 10건씩 60초 넣으면
- **Then** 모든 요청이 접수되고, 720건 모두 재고·포인트·결제가 정확히 한 번씩이다.
- **Then** 결제가 밀리지 않고, 마지막 요청 뒤 약 11초 안에 모두 끝난다.

## 한계

- 0.15초마다 읽었으므로 시간에는 ±0.15초 오차가 있다.
- 장애 시간을 90초 (S5·S8), 120초 (S7)로 고정했으므로 결제 완료까지 걸린 시간은 장애 길이에 비례한다.
- 시나리오마다 한 번씩 쟀다. 부하는 초당 4건과 초당 10건만 걸었다.
- S10과 S12는 측정 스크립트 오류로 첫 결과를 버리고 다시 쟀다. 시스템 동작과는 무관하다.
- 2026-09-26 코드 기준이다. 코드나 재시도·복구 설정을 바꾸면 수치도 바뀐다.
